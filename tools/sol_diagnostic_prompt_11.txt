### 2.2 Analisi del Meccanismo
In `unified_native_decoder.py`:
- Linea 760-762:
  ```python
  except BaseException:
      self._failed = True
      raise
  ```
- Linee 249-250 (`_live`):
  ```python
  if self._failed:
      raise RuntimeError("native generation session failed; close it before reuse")
  ```
- Linea 501-503 (`advance`):
  ```python
  if self._final_step is not None:
      return self._replay_terminal_step()
  decoder, state = self._live()
  ```

In `server_unified_thinker.py` (linee 1257-1270):
```python
if not callable(candidate_ready_when):
    try:
        while True:
            step = advance_controller(lambda _progress: False)
            handoff = handoff_adopted_session()
            if handoff is not None:
                return handoff
            if step.status in {NativeDecodeSessionStatus.DONE, NativeDecodeSessionStatus.CANCELLED}:
                return finish_decoded(step.result)
    except BaseException as exc:
        handoff = handoff_adopted_session(exc)
        if handoff is not None:
            return handoff
        raise
```
E in `handoff_adopted_session(exc)`:
```python
adopted_controller = unified_branch.get("_adopted_native_session_controller")
if isinstance(adopted_controller, dict):
    resume = adopted_controller.get("run_to_completion")
    if callable(resume):
        result = resume()
```
Se `advance_controller` lancia un'eccezione (ad es. per cancellazione, timeout o abort), `self._failed` viene impostato a `True`.
Quando poi `handoff_adopted_session` o `server_response_runtime.py:2553` chiama `resume()` (ossia `run_controller_to_completion`), questo invoca nuovamente `advance_controller(lambda _progress: False)`.
Poiché `self._failed` è `True` e `self._final_step` non è stato impostato come terminale (perché l'eccezione è stata sollevata prima di `_terminate`), `advance()` richiama `_live()`, che solleva `RuntimeError: native generation session failed; close it before reuse`, provocando la rottura catastrofica della connessione WebSocket con `INFERENCE_ERROR`.

### 2.3 Domanda per Sol su Errore 1:
Come deve essere strutturato il contratto di chiusura, finalizzazione e handoff di `UnifiedNativeDecoderSession` e `run_controller_to_completion` affinché:
1. Una sessione di decodifica nativa che subisce una cancellazione o eccezione non rimanga in uno stato intermedio "zombie" (`_failed = True` ma priva di `_final_step`)?
2. `run_controller_to_completion()` o `resume()` sia idempotente e non tenti mai di richiamare `advance()` su una sessione già fallita o cancellata, restituendo invece un risultato coerente di cancellazione/revisione (`revision_handoff: True`) senza mandare in crash il server?

## 3. Errore 2 (Run 2): Picco ACK Gap di 182.3 ms sul Frame 1128 (Ultimo Frame Audio)

### 3.1 Dati Empirici
In Run 2:
- Totale frame audio della richiesta lunga: **1129 frame** (da `local_frame_id = 0` a `local_frame_id = 1128`).
- Tutti i frame intermedi da 0 a 1127 hanno registrato ACK gap inferiori alla soglia (compreso il frame 664 che in passato dava 161.9 ms e ora è sceso a ~134 ms).
- **Solo la transizione tra frame 1127 e frame 1128** ha registrato:
  `Gap 182.27ms between Frame 1127 and Frame 1128`

### 3.2 Cronologia di Frame 1127 e 1128 (`events.jsonl`)
- `22:16:48.648057`: Frame 1127 inviato dal client (`input_frame_sent`).
- `22:16:48.701079`: Frame 1127 consumato dal server (`input_audio_buffer.consumed`).
- `22:16:48.703760`: Frame 1127 ACK ricevuto dal client (`input_frame_ack_received`).
- `22:16:48.729745`: Frame 1128 inviato dal client (`input_frame_sent`).
- `22:16:48.883349`: Frame 1128 consumato dal server (`input_audio_buffer.consumed`).
- `22:16:48.885612`: Frame 1128 ACK ricevuto dal client (`input_frame_ack_received`).

Il delta tra l'ACK di 1127 e l'ACK di 1128 è `48.885612 - 48.703760` = **181.85 ms** (nel report registrato come **182.3 ms**).

### 3.3 Scomposizione Telemetrica di Frame 1128
Dal payload di `input_audio_buffer.consumed` di frame 1128:
- `server_listener_queue_ms`: **117.568 ms** (il tempo trascorso in coda sul server prima dell'inizio del compute del batch).
- `listener_batch_compute_ms`: **111.071 ms** (contro i ~25-45 ms dei frame normali).
  - `listener_batch_frontend_encode_ms`: **22.689 ms** (normale: ~1.6 ms)
  - `listener_batch_mel_prepare_ms`: **21.332 ms** (normale: ~0.8 ms)
  - `listener_batch_native_submit_ms`: **24.254 ms** (normale: ~12.0 ms)
  - `listener_batch_native_cuda_ms`: **23.330 ms** (normale: ~12.4 ms)
  - `listener_batch_control6_policy_ms`: **2.912 ms** (normale: ~1.6 ms)
  - `scheduler_commit_state_lock_hold_ms`: **5.535 ms** (normale: ~0.8 ms)
- Subito dopo il frame 1128, il flusso audio in ingresso termina e il sistema transita alla risposta Thinker/Talker.
- In Run 3, invece, questo picco non si è verificato e tutti i frame (incluso il frame 1128) sono stati processati ampiamente sotto i 160 ms.

### 3.4 Domanda per Sol su Errore 2:

È imputabile a contesa CPU/GIL per l'avvio della transizione di fine stream/endpointing, o al Talker che stava completando il drain precedente o preparando lo step successivo?
